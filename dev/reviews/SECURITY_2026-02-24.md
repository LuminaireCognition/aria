### 1) SECURITY_001 #3 Regression: `authenticated` level re-enabled in policy defaults and config

- **Severity:** Medium-High
- **Likelihood:** High (present in both code defaults and config file)
- **Confidence:** High
- **CVSS-like score:** 6.5
- **Blast radius:** All authenticated ESI endpoints (wallet, assets, skills, mining ledger) accessible without explicit user opt-in
- **Attack vector:** Prompt injection via persona file, tool output, or cached data causes the LLM to invoke authenticated API calls. Since the policy permits `AUTHENTICATED` by default, no confirmation gate fires.
- **Risk summary:** SECURITY_001 Finding #3 documented the removal of `authenticated` from `allowed_levels` in `reference/mcp-policy.json` and the addition of a `require_confirmation` mechanism. However, the current state of both the code and the configuration file shows `authenticated` is back in `allowed_levels`, completely negating the previous mitigation.
- **Evidence:**
  - `reference/mcp-policy.json:5-10`: `allowed_levels` includes `"authenticated"`
  - `src/aria_esi/mcp/policy.py:211-218`: `PolicyConfig` default includes `SensitivityLevel.AUTHENTICATED`
  - `src/aria_esi/mcp/policy.py:240-243`: `from_dict()` fallback list includes `"authenticated"`
  - `reference/mcp-policy.json:11`: `require_confirmation` is empty `[]`
  - SECURITY_001 Finding #3 claims: "Removed `authenticated` from `allowed_levels` in `reference/mcp-policy.json`" -- this is contradicted by the current file
- **Attack scenario:**
  1. Attacker embeds indirect prompt injection in a cached mission briefing or market data response.
  2. Injected instruction requests the LLM to call `pilot(action="mail_list")` or `pilot(action="mining_ledger")`.
  3. Policy engine checks sensitivity: `mining_ledger` is `AUTHENTICATED`, which is in `allowed_levels`.
  4. No `ConfirmationRequired` is raised because `require_confirmation` is empty.
  5. Personal data is retrieved and potentially exfiltrated via the LLM response.
- **Mitigations (ranked):**
  1. Remove `"authenticated"` from `allowed_levels` in `reference/mcp-policy.json` and from the `PolicyConfig` default.
  2. Add `"authenticated"` to `require_confirmation` in `reference/mcp-policy.json`.
  3. Update the `from_dict()` fallback to exclude `authenticated` from the default list.
  4. Add a regression test that asserts `AUTHENTICATED` is not in the default `allowed_levels`.
- **Tradeoffs/side effects:** Users will see confirmation prompts when accessing personal ESI data. This is the intended secure-by-default behavior.
- **Recommendation:** Restore the SECURITY_001 mitigation and add a regression test to prevent future regressions.
- **Verification plan:** Unit test asserting `SensitivityLevel.AUTHENTICATED not in PolicyConfig().allowed_levels`. Integration test confirming `ConfirmationRequired` is raised for `pilot.mining_ledger`.

### 2) Shell injection in boot scripts via unescaped JSON embedded in Python heredoc

- **Severity:** Medium
- **Likelihood:** Low-Medium (requires attacker control of CLI output)
- **Confidence:** Medium
- **CVSS-like score:** 5.5
- **Blast radius:** Arbitrary code execution during session boot
- **Attack vector:** If the JSON output from `aria-esi verify-persona-context` or `aria-esi validate-overlays` contains crafted content (e.g., triple-quote sequences), it can break out of the Python triple-quoted string in the boot script.
- **Risk summary:** The boot scripts embed CLI JSON output directly into Python triple-quoted strings using bash variable interpolation (`$verify_json`). If the JSON contains `'''` (triple single quotes), it terminates the Python string literal and allows arbitrary Python code execution.
- **Evidence:**
  - `.claude/hooks/aria-boot.d/boot-operations.sh:214`: `data = json.loads('''$verify_json''')`
  - `.claude/hooks/aria-boot.d/boot-operations.sh:330`: `data = json.loads('''$validation_json''')`
  - Both lines embed the raw bash variable `$verify_json` / `$validation_json` inside Python `'''` delimiters without escaping.
- **Attack scenario:**
  1. Attacker modifies a persona source file to contain content that, when the `verify-persona-context` command processes it, produces JSON output containing `'''`.
  2. Boot script runs `json.loads('''<JSON-with-triple-quotes>''')`.
  3. The triple quotes inside the JSON terminate the Python string. Subsequent content is interpreted as Python code.
  4. Arbitrary Python code runs under the boot user's privileges.
- **Mitigations (ranked):**
  1. Pass JSON to Python via stdin pipe instead of string interpolation: `echo "$verify_json" | uv run python -c "import json, sys; data = json.load(sys.stdin); ..."`.
  2. Alternatively, use `base64` encoding/decoding to safely transport arbitrary strings.
  3. If string interpolation is required, escape `'` characters in the bash variable before embedding.
- **Tradeoffs/side effects:** Minimal. Stdin piping is more robust and a standard pattern.
- **Recommendation:** Replace all bash-variable-in-Python-string patterns with stdin piping.
- **Verification plan:** Add a test with a persona file containing `'''` in its content and verify boot completes without code injection.

### 3) Residual pickle deserialization via igraph Read_Picklez

- **Severity:** Medium
- **Likelihood:** Low (requires file system write access to the universe graph)
- **Confidence:** High
- **CVSS-like score:** 5.0
- **Blast radius:** Remote code execution on graph load
- **Attack vector:** Replace or modify the `.universe` graph file's embedded igraph binary section to contain a malicious pickle payload.
- **Risk summary:** SECURITY_000 Finding #3 migrated from raw `pickle.load()` to a safe `.universe` format using msgpack. However, the graph topology itself is still deserialized using `ig.Graph.Read_Picklez()` (line 150 of `serialization.py`), which internally uses Python's pickle. The msgpack container provides format validation and checksums, but the graph binary within the container is still pickle-based. A sufficiently motivated attacker who can modify the `.universe` file could craft a payload that passes the msgpack/magic-byte checks but exploits the pickle deserialization.
- **Evidence:**
  - `src/aria_esi/universe/serialization.py:148-150`: `graph = ig.Graph.Read_Picklez(graph_buffer)`
  - `src/aria_esi/universe/serialization.py:79-80`: Graph serialized with `graph.write_picklez(graph_buffer)`
  - SECURITY_000 Finding #3 "Remaining risks": "igraph internal serialization still uses pickle (limited scope, embedded in msgpack container)"
- **Attack scenario:**
  1. Attacker gains write access to `src/aria_esi/data/universe.universe` or sets `ARIA_UNIVERSE_GRAPH` to a crafted file.
  2. The outer msgpack container is validly formed (magic bytes, metadata).
  3. The embedded graph bytes contain a malicious pickle payload.
  4. On MCP server startup, `Read_Picklez()` deserializes and executes the payload.
- **Mitigations (ranked):**
  1. Migrate to igraph's GraphML, GML, or adjacency list format (no pickle). Performance impact is acceptable for a one-time load.
  2. Add a pre-deserialization checksum of the graph bytes section specifically, verified against a committed manifest.
  3. Restrict `ARIA_UNIVERSE_GRAPH` to hardcoded paths only (no environment override).
  4. Ensure the committed `.universe` file is protected by CI integrity checks.
- **Tradeoffs/side effects:** Format migration requires rebuilding the graph file. GraphML/GML may be slightly larger but eliminates the pickle attack surface entirely.
- **Recommendation:** Migrate igraph serialization to a non-pickle format (GraphML or edge list). This fully closes SECURITY_000 Finding #3.
- **Verification plan:** After migration, `grep -r "pickle" src/aria_esi/universe/` should return zero results. Unit test loading a crafted malicious graph file should raise an error, not execute code.

### 4) Data integrity verification soft-fails when no checksum is configured

- **Severity:** Medium
- **Likelihood:** Medium (new data sources start without checksums)
- **Confidence:** High
- **CVSS-like score:** 4.5
- **Blast radius:** Supply chain poisoning of SDE/EOS data
- **Attack vector:** Introduce a new data source or clear the checksum from `reference/data-sources.json`. Integrity verification silently passes.
- **Risk summary:** The `verify_sde_file()` function in `data_integrity.py` passes verification with only a log warning when no expected checksum is configured in the manifest. This means any newly added data source, or one whose checksum entry is removed, bypasses integrity verification entirely without raising an error.
- **Evidence:**
  - `src/aria_esi/core/data_integrity.py:257-261`: When `expected_checksum is None`, verification returns `(True, actual)` -- a successful result with no integrity guarantee.
  - Comment says "Phase 1 rollout" suggesting this was intended as temporary.
- **Attack scenario:**
  1. Attacker removes or corrupts the checksum entry in `reference/data-sources.json` via a PR or local modification.
  2. `verify_sde_file()` is called and returns success because there is no expected checksum.
  3. A tampered SDE database is loaded without detection.
  4. Poisoned data flows into LLM tool responses, enabling indirect prompt injection.
- **Mitigations (ranked):**
  1. Fail-closed: raise `IntegrityError` when no checksum is configured (require explicit opt-out via break-glass).
  2. Add a CI check that verifies all data sources in `reference/data-sources.json` have non-null checksums.
  3. Log at WARNING or ERROR level (currently INFO) to increase visibility.
- **Tradeoffs/side effects:** New data sources would need checksums added before first use, adding a manual step to the workflow.
- **Recommendation:** Change the default behavior to fail-closed. The break-glass `ARIA_ALLOW_UNPINNED=1` already exists for legitimate bypass.
- **Verification plan:** Unit test: call `verify_sde_file()` with no checksum in manifest, assert `IntegrityError` is raised. CI test: validate all manifest entries have checksums.

### 5) Audit log sanitization gaps in policy engine

- **Severity:** Medium
- **Likelihood:** Medium (depends on log aggregation and access)
- **Confidence:** High
- **CVSS-like score:** 4.0
- **Blast radius:** Token/credential leakage in log files
- **Attack vector:** Sensitive data flows through audit logs unsanitized.
- **Risk summary:** The policy engine's audit log sanitization (`_audit_log` method) uses an exact key blocklist of only `"password"`, `"token"`, and `"secret"`. This misses common credential key names like `access_token`, `refresh_token`, `api_key`, `authorization`, and `bearer`. Meanwhile, the context module's `_sanitize_params()` function uses a more comprehensive substring-match approach checking for `"token"`, `"password"`, `"secret"`, `"key"`, `"auth"` as substrings of key names. The two sanitization approaches are inconsistent.
- **Evidence:**
  - `src/aria_esi/mcp/policy.py:486-488`: `k not in ("password", "token", "secret")` -- exact match only.
  - `src/aria_esi/mcp/context.py:675-682`: `any(s in key_lower for s in sensitive_keys)` -- substring match against `{"token", "password", "secret", "key", "auth"}`.
  - The context.py approach would catch `access_token`, `api_key`, `authorization`; the policy.py approach would not.
- **Mitigations (ranked):**
  1. Unify sanitization: extract the `_sanitize_params()` logic from `context.py` into a shared utility and use it in both places.
  2. At minimum, update the policy audit log to use substring matching with the same key set.
  3. Add a test with a context dict containing `{"access_token": "secret123"}` and verify it is redacted.
- **Tradeoffs/side effects:** None. This is purely a defensive improvement.
- **Recommendation:** Create a shared `sanitize_sensitive_keys()` utility and use it in both `policy.py` and `context.py`.
- **Verification plan:** Unit test: pass `{"access_token": "abc", "refresh_token": "xyz", "api_key": "123"}` to the audit logger. Assert all values are redacted in the output.

### 6) Rate limiting defaults to unlimited (0) with no enforcement path

- **Severity:** Low-Medium
- **Likelihood:** Medium (prompt injection could trigger rapid tool calls)
- **Confidence:** Medium
- **CVSS-like score:** 3.5
- **Blast radius:** Resource exhaustion, excessive ESI/external API calls, potential API key rate-limit bans
- **Attack vector:** Prompt injection causes the LLM to repeatedly call MCP tools in a loop.
- **Risk summary:** The policy engine implements rate limiting infrastructure (`rate_limit_per_minute` field, `_call_counts` tracking dict), but the default is 0 (unlimited) in both the code and the config file. While the Claude Code client may impose its own limits, the MCP server itself has no defense against excessive tool invocation.
- **Evidence:**
  - `src/aria_esi/mcp/policy.py:234`: `rate_limit_per_minute: int = 0`
  - `reference/mcp-policy.json:15`: `"rate_limit_per_minute": 0`
  - The rate limit check logic exists but `0` means unlimited.
- **Mitigations (ranked):**
  1. Set a reasonable default rate limit (e.g., 60 calls/minute for most dispatchers, 10/minute for authenticated).
  2. Add per-dispatcher rate limits rather than a global limit.
  3. Add exponential backoff on repeated failures.
- **Tradeoffs/side effects:** May impact rapid legitimate queries. Choosing a generous default (60/min) mitigates this.
- **Recommendation:** Set a default rate limit of 60 calls/minute globally and 10/minute for authenticated actions.
- **Verification plan:** Integration test: submit 65 tool calls in rapid succession, verify the 61st is rate-limited.

### 7) SDE importer constructs SQL via f-string interpolation

- **Severity:** Low-Medium
- **Likelihood:** Low (column names come from SQLite PRAGMA, not user input)
- **Confidence:** Medium
- **CVSS-like score:** 3.0
- **Blast radius:** SQL injection if SDE database is attacker-controlled
- **Attack vector:** A compromised upstream SDE database contains table column names that include SQL injection payloads.
- **Risk summary:** The SDE importer uses f-strings to construct SQL queries with column names derived from `PRAGMA table_info()` results. While these values come from the database schema (not direct user input), if the SDE database itself is compromised (which is the attack vector that checksum verification was designed to prevent), column names could contain injection payloads.
- **Evidence:**
  - `src/aria_esi/mcp/sde/importer.py:730-734`:
    ```python
    cursor = sde_conn.execute(f"""
        SELECT {bp_col}, {prod_col}, {qty_col}
        FROM industryActivityProducts
        WHERE activityID = 1
    """)
    ```
  - Column names (`bp_col`, `prod_col`, `qty_col`) are derived from pragma results without quoting.
- **Mitigations (ranked):**
  1. Use SQLite identifier quoting: `f'SELECT "{bp_col}", "{prod_col}", "{qty_col}"'` (double-quotes for identifiers).
  2. Validate column names against an allowlist of expected names before interpolation.
  3. Use a query builder that handles identifier escaping.
- **Tradeoffs/side effects:** Minimal. Adding quotes around identifiers is a standard SQLite practice.
- **Recommendation:** Add identifier quoting and/or allowlist validation for column names.
- **Verification plan:** Code review to confirm all f-string SQL uses quoted identifiers. Unit test with a mocked database returning a malicious column name.

### 8) Multiple break-glass environment variables lack centralized audit trail

- **Severity:** Low-Medium
- **Likelihood:** Low (requires environment access)
- **Confidence:** Medium
- **CVSS-like score:** 3.0
- **Blast radius:** Full bypass of path security, data integrity, and MCP policy
- **Attack vector:** Attacker sets environment variables to disable security controls.
- **Risk summary:** Three break-glass environment variables can individually disable major security controls: `ARIA_ALLOW_UNSAFE_PATHS` (path validation bypass), `ARIA_ALLOW_UNPINNED` (integrity check bypass), and `ARIA_MCP_BYPASS_POLICY` (policy engine bypass). While each is logged individually, there is no centralized audit mechanism that detects when multiple are active simultaneously, which would indicate a targeted security bypass.
- **Evidence:**
  - `src/aria_esi/core/path_security.py`: `ARIA_ALLOW_UNSAFE_PATHS` bypasses path validation
  - `src/aria_esi/core/data_integrity.py`: `ARIA_ALLOW_UNPINNED` bypasses checksum verification
  - `src/aria_esi/core/config.py:202`: `mcp_bypass_policy` / `ARIA_MCP_BYPASS_POLICY`
  - `src/aria_esi/mcp/policy.py:331-333`: `is_bypass_enabled()` checks config
- **Mitigations (ranked):**
  1. Add a boot-time check that logs a prominent warning when any break-glass variable is active.
  2. Add a check that refuses to start (or requires explicit confirmation) when two or more break-glass flags are active simultaneously.
  3. Record break-glass state in the session context for audit purposes.
- **Tradeoffs/side effects:** Could block legitimate debugging workflows if too strict. A warning-only approach avoids this.
- **Recommendation:** Add a boot-time aggregated break-glass check with prominent warning output.
- **Verification plan:** Set all three env vars and verify boot logs contain a prominent security warning. Set two and verify a multi-bypass warning.

### 9) JSON logging dumps arbitrary record fields without sanitization

- **Severity:** Low
- **Likelihood:** Low (requires sensitive data in log record extras)
- **Confidence:** Medium
- **CVSS-like score:** 2.5
- **Blast radius:** Credential leakage in structured logs
- **Attack vector:** A log record containing sensitive data in extra fields is serialized to JSON output.
- **Risk summary:** The JSON log formatter iterates over all `record.__dict__` items and includes any key not in a hardcoded exclusion list. If a library or application code adds sensitive data (tokens, credentials) as extra fields on a log record, they will be serialized to JSON logs without redaction.
- **Evidence:**
  - `src/aria_esi/core/logging.py:99-123`: Iterates over `record.__dict__` items, excluding only standard Python logging fields.
  - No sanitization of values or key-name filtering for sensitive patterns.
- **Mitigations (ranked):**
  1. Apply the same sensitive-key sanitization used in `context.py:_sanitize_params()` to log record extras.
  2. Use an explicit allowlist of extra fields rather than a blocklist of standard fields.
  3. Add a log filter that redacts values for keys matching sensitive patterns.
- **Tradeoffs/side effects:** Allowlist approach may miss legitimate extra fields. Sanitization approach is more compatible.
- **Recommendation:** Add sensitive-key redaction to the JSON formatter using the shared sanitization utility (see Finding #5).
- **Verification plan:** Create a log record with `extra={"access_token": "secret"}` and verify JSON output contains `[REDACTED]`.

## Top 5 Quick Wins (1-2 days)

1. **Restore SECURITY_001 #3 mitigation:** Remove `"authenticated"` from `allowed_levels` in both `reference/mcp-policy.json` and the `PolicyConfig` default. Add regression test. (Finding #1, ~1 hour)

## Medium-Term Fixes (1-2 weeks)

- **Migrate igraph serialization away from pickle:** Replace `Read_Picklez`/`write_picklez` with GraphML, edge list, or a custom binary format. This fully closes the pickle attack surface. (Finding #3)

- **Fail-closed on missing checksums:** Change `verify_sde_file()` to raise `IntegrityError` when no checksum is configured, rather than silently passing. (Finding #4)

- **Centralized break-glass audit:** Add boot-time detection and warning when break-glass environment variables are active, especially in combination. (Finding #8)

- **Per-dispatcher rate limits:** Implement differentiated rate limits (higher for public data, lower for authenticated/external API calls).

## Long-Term Architectural Controls

- **Eliminate all pickle usage:** Complete migration to safe serialization formats across the entire codebase. No `pickle.load`, `pickle.loads`, or libraries that use pickle internally.

- **Structured log sanitization pipeline:** Centralized log sanitization that applies across all formatters and destinations, with configurable redaction patterns.

- **Policy-as-code with version control:** Move from a JSON config file to a validated policy schema with schema versioning, migration tooling, and CI enforcement of security invariants (e.g., "authenticated must not be in allowed_levels").

- **Sandboxed MCP server:** Run the MCP server in a restricted environment (container, seccomp, or similar) with constrained filesystem access and network egress limited to known endpoints (ESI API, zKillboard, Fuzzwork).

- **Regression test suite for security invariants:** A dedicated test module that asserts security properties: default policy excludes authenticated, break-glass variables are not set in CI, all data sources have checksums, no pickle usage in production code.

## Notes / Assumptions

- Static review only; no code execution performed.
- Assumed the runtime follows the documented persona/skill loading flow and has local file/tool access.
- The authenticated-level regression (Finding #1) is the highest priority item. It represents a regression from a previously-resolved security finding, which suggests the mitigation was reverted (possibly intentionally during development) but not re-applied before release.
- The shell injection risk (Finding #2) has low practical likelihood because the JSON output comes from trusted CLI commands, but the pattern is inherently unsafe and should be corrected as a matter of defense in depth.
- The pickle residual risk (Finding #3) was documented in SECURITY_000 as a remaining risk. This audit elevates it to a formal finding because a complete migration to non-pickle formats is feasible and would fully close the attack surface.
- All findings are based on the codebase at commit `12b7172f` (branch `fix/benchmark-coverage-failure`).
